## 一、为什么直接跳 v1.1.1，不走 v1.1.0

| 维度 | v1.1.0（2026-04-24） | v1.1.1（2026-05-07） |
|------|---------------------|---------------------|
| 距今 | 3 周 | 1 周 |
| 与本项目 workaround 重叠的修复 | 4 项 | **4 项 + 增量 4 项** |
| MinIO bootstrap 行为 | **可能损坏**（详见下文） | 已修复 |
| Manager 配置覆盖问题 | 部分修复 | `observe-recovery` 禁用，用户改动不再被回卷 |
| 升级路径安全性 | 自动迁移 | 加上 "manager 停机时提取 Matrix 凭证" |
| 社区反馈窗口 | 当时零反馈 | 已收过一轮反馈，由 v1.1.1 吸收 |

**核心判定**：v1.1.0 是必经的架构跃迁（all-in-one → 多容器 + CRD），v1.1.1 把 v1.1.0 首发暴露的几个 ops-level bug 都修了。**直接安装 v1.1.1 风险严格小于安装 v1.1.0**，且原本计划的"等 1–2 周社区反馈"窗口已经天然走完。

## 二、v1.1.1 关键变化（相对 v1.1.0 的增量）

数据来源：[HiClaw v1.1.1 release notes](https://github.com/agentscope-ai/HiClaw/releases/tag/v1.1.1)（12 commits since v1.1.0，发布人 @Jing-ze）。

### 2.1 直接利好本项目的 Bug 修复

| v1.1.1 修复 | 命中本项目位置 | 影响 |
|------------|---------------|------|
| **MinIO S3 endpoint 修正为 :9000（原 :8080）** | `deploy/hiclaw/init-workers.sh`（worker 配置写入 MinIO）、`deploy/hiclaw/manager-init-internal.sh` | 如果直接跳 v1.1.0，worker bootstrap 大概率因端口错误静默失败 |
| **Local-first openclaw.json merge（bash + hermes）** | `manager-init-internal.sh` 整段 post-startup patch（DM allowlist、`memorySearch` pop、`baseUrl` 模板） | 多个 patch 步骤可以收敛为"写一次、原地保留"，容器重建不再回卷 |
| **Runtime-aware task dispatch；避免 admin DM 里 @worker** | PR #56（`53de303 fix(hiclaw): stabilize v1.0.9 dispatch path before 1.1.0 upgrade`）所修的同一类问题 | 上游正式接住，长期可下线本地 dispatch 稳定化补丁 |
| **Manager 停机时提取 Matrix 凭证** | 1.0.9 → 1.1.x in-place 升级路径本身 | 降低 per-user Matrix 账号在迁移阶段丢凭证的概率 |
| **`spec.env` 在 Worker/Manager/Team CR 上被尊重** | 当前所有 env 都通过 `init-workers.sh` 写 `openclaw.json` | 后续可以把 `HICLAW_LLM_PROVIDER=openai-compat`、`HICLAW_AI_GATEWAY_SERVER` 等下沉到 CR 声明 |
| **K8s 409 conflict + 乐观更新重试** | `deploy/k8s/hiclaw/*.yaml`、`deploy/k8s/jobs/init-workers.yaml` | 一旦切到 k3s/ECS，控制面冲突自愈，省去手工排查 |
| **`mc mirror` 前校验 agent 目录存在** | `init-workers.sh` 把 `openclaw.json + SOUL.md + AGENTS.md` 写入 MinIO 的步骤 | 减少"目录不存在 → mirror 静默吞错"的隐性失败 |
| **`observe-recovery` 禁用，用户配置变更不被回卷** | 我们对 manager `openclaw.json` 的所有外置 patch | 上游不再覆盖我们写入的字段 |

### 2.2 新能力（用得上的）

- `mcpServers` 支持挂在 Team Leader 规格上 —— 与本项目 honeybadge-nebula-mcp / honeybadge-audit-mcp / honeybadge-cache-mcp 的挂载策略相关，**升级时一并评估**。
- `ContainerManaged` 字段允许管理「非容器化 worker」—— 不立即用，但保留为未来 analytics-worker 切外置 runtime 时的逃生通道。
- worker package 解包可选包含 `SOUL.md` —— 我们已经在做这件事，正好对齐上游。
- 多架构镜像（amd64 + arm64）—— Apple Silicon 本地开发顺手。

### 2.3 破坏性变化（**升级前必须验证**）

> **"Restructure mcpServers on Worker/Manager/Team CRDs and drop controller-side MCP authorization"**

本项目影响面：

- 三个 MCP server 通过 worker `openclaw.json` 的 `mcpServers` 字段挂载：
  - `honeybadge-nebula-mcp`（NebulaGraph 查询）
  - `honeybadge-audit-mcp`（PostgreSQL 审计写入）
  - `honeybadge-cache-mcp`（Redis 缓存）
- 控制面侧 MCP 授权被移除 → 当前如果依赖 HiClaw controller 校验 MCP server 的 allow-list，现在要在 **应用层** 自己确认。本项目目前是直连 SSE :8000，没用 controller-side 授权，**预计无功能影响**，但需要验证 `mcpServers` block 的新 schema。

### 2.4 v1.1.0 → v1.1.1 一并继承的架构跃迁

（这些是 v1.1.0 的内容，但因为我们跳过 v1.1.0，所以在 v1.1.1 升级时一次性承受）

- Manager 单容器 all-in-one → **多容器 + K8s 原生控制面**（Tuwunel / MinIO / Higress / Element Web 迁入 `hiclaw-embedded`，Manager 镜像 −1.7 GB）
- `workers-registry.json` → CRD（`wk` / `tm` / `hm` / `mgr`），首次启动自动迁移
- Controller 不再每 5 分钟轮换 Matrix token（v1.1.0 修，v1.1.1 继承）
- `allowedConsumers` 在重启时不再被清空（v1.1.0 修）
- `HICLAW_DEFAULT_MODEL` 真正被 `hiclaw create worker` 尊重（v1.1.0 修）
- Manager 身份修正为 `@manager`（v1.1.0 修；原 `@default` 丢失 admin DM）

## 四、收益评估

**硬收益（可量化）：**
- Manager 镜像体积 −1.7 GB；ECS 8 GB 节点 pull 与磁盘有感
- 至少 **6 处** patch 可删（详见 §5.2），脚本行数预计减少 30–40%
- `MinIO :9000` 与 `local-first merge` 修复让"容器重建后 DM allowlist 回到 `[@admin]`"的运维痛点消失（CLAUDE.md 已记录此 gotcha）
- 上游接管 dispatch 稳定化，可下线 PR #56 中的兜底逻辑

**软收益：**
- 控制面与 Phase 1 方向对齐（CRD + Helm）
- 多架构镜像（amd64 + arm64）让本地 Mac 开发体验改善
- `spec.env` 下沉，env-var 管理从脚本侧迁到声明侧
- 为 analytics-worker 切 Hermes runtime 留出空间

**风险：**
- `mcpServers` CRD 重构是真正的破坏性变化；本项目三个 MCP server 的挂载方式必须在分支内验证
- 单步从 1.0.9 跳到 1.1.1 跨越了 v1.1.0 的架构变化，自动迁移路径在本项目实际拓扑上未亲测
- ECS 单节点 8 GB 内存下多容器拆分，资源占用需在阶段 1 用 `docker stats` 实测后再确认 K8s `resources.requests`

## 六、遗留问题：`memorySearch` 的定位

> 本节直接继承自 `docs/1.1.0-upgrade-suggestion.md` §六，结论与决策矩阵不变。这里只补充 v1.1.1 视角下的差异。

### 当前状态（v1.0.9，已合入 master）

`manager-init-internal.sh` 在启动期把 `agents.defaults.memorySearch` 整段移除。原因链条（TC105 根因）：HiClaw v1.0.9 模板注入了 `memorySearch.remote.baseUrl = http://aigw-local.hiclaw.io:8080/v1` 走 `/v1/embeddings`，但 Higress 只路由 `/v1/chat/completions`，导致 Node `new URL()` 抛 `TypeError: Invalid URL`，整条 agent run 在第一条用户消息到达时就被打死。

### v1.1.1 视角下的新信息

- v1.1.1 的 **"Local-first openclaw.json merge"** 让我们的 pop 操作只需要做一次，不会被 controller reconcile 回卷 —— 这意味着即便 v1.1.1 模板仍然注入 memorySearch 默认值，我们的处理方式可以从"启动期 pop" 简化为"一次性写入 + 永久生效"。
- **MinIO endpoint 修正为 :9000** 不直接影响 memorySearch，但意味着如果未来真要启用运维型记忆，memory 文件持久化路径（MinIO → manager workspace）这条链路的端口现在是统一的。
- **阶段 1 必做**：在本地拉起 v1.1.1 后立即 `cat /root/manager-workspace/openclaw.json`，确认 `agents.defaults.memorySearch` 是否仍被注入；如果上游已改为「未配置 embedding provider 时不注入」，那本项目的 pop 代码可以直接删。

### 决策矩阵（保持原表，三选一）

| 场景 | SOUL 禁令 | runtime memorySearch 配置 | Higress embeddings 路由 | memory 文件 |
|---|---|---|---|---|
| **现状（保持方案）** | 全禁 | 移除 | 不加 | 无 |
| **只解禁运维型记忆** | 限定"ERP 业务数据" | 保留 + 指向真实 embedding | 加 | 加 + 明确写入策略 |
| **完全解禁（不推荐）** | 删禁令 | 保留 | 加 | 加 |

> **v1.1.1 升级时的动作项**：阶段 1 本地验证时确认 v1.1.1 模板的 `memorySearch` 默认行为，再决定走哪一列。**不要把此决策和 v1.1.1 升级 blocker 混在一起做**。
