## 一、为什么直接升 v1.1.2，不走 v1.1.1

| 维度 | v1.1.1（2026-05-07） | v1.1.2（2026-05-27） |
|------|---------------------|---------------------|
| 距今 | 7 周 | 4 周 |
| 破坏性变化 | `mcpServers` CRD 重构 | **无新破坏性** |
| 社区反馈窗口 | 1 周 | 4 周（吸收 v1.1.1 首批反馈） |
| 增量 bug 修复 | — | `groupAllowFrom` 热加载、CoPaw 启动期消息吞掉、controller reconcile 保留 runtime mutation、TokenReview cache 上限、Higress stream idle timeout |

| Team Leader skill alias | 保留 | **移除旧 alias**（需检查 SOUL.md / SKILL.md 是否引用） |

**核心判定**：v1.1.2 是 v1.1.1 的纯增量 patch，无新破坏性变化，且吸收了 v1.1.1 发布 4 周的社区反馈。**直接升 v1.1.2 风险严格小于"先升 v1.1.1 再升 v1.1.2"**，也小于"只升 v1.1.1"。

## 二、v1.1.0 → v1.1.2 关键变化

### 2.1 v1.1.1 的破坏性变化（阶段 1 必验证 —— 硬 blocker）

> **"Restructure mcpServers on Worker/Manager/Team CRDs and drop controller-side MCP authorization"**

**✅ 阶段 1 验证结果（2026-06-25）：硬 blocker 已清除。**

验证方法：对比 v1.1.0 运行中容器与 v1.1.2 镜像内的模板文件、MCP 配置源码、编译后 JS。

| 对比项 | 结果 |
|--------|------|
| `generate-worker-config.sh` | IDENTICAL |
| `worker-openclaw.json.tmpl` | IDENTICAL |
| `manager-openclaw.json.tmpl` | IDENTICAL |
| `mcp-config.ts` / `types.mcp.ts` | IDENTICAL |
| `mcp-config-BXbuLA0x.js`（编译后） | md5sum 相同 |
| MCP/mcporter 文件列表 | 逐行完全相同 |

**关键发现**：
1. v1.1.0 worker `openclaw.json` 本身不含 `mcpServers` 字段 —— MCP 配置通过独立的 `mcporter.json` 管理（WS-19/WS-20 做法）
2. v1.1.1 的 "Restructure mcpServers on CRDs" **只影响 K8s CRD 控制面**，不影响 docker-compose 模式
3. WS-19/WS-20 **无需修改**

详见 `UPGRADE-NOTES.md` §1.2 和 `docs/baselines/v1.1.0/` + `docs/baselines/v1.1.2/` 的模板文件。

原本预计的影响面（已证伪，保留作历史参考）：

- ~~三个 MCP server 通过 worker `openclaw.json` 的 `mcpServers` 字段挂载~~ —— 实际通过 `mcporter.json` 挂载
- ~~控制面侧 MCP 授权被移除~~ —— 本项目直连 SSE :8000，未用 controller-side 授权，无影响
- ~~需要验证 `mcpServers` block 的新 schema~~ —— schema 未变（IDENTICAL）

### 2.3 v1.1.2 增量（无破坏性，继承自 v1.1.1）

新能力（用得上的）：

- **QwenPaw-first 安装器**：keep-all 升级，enter-to-keep 提示已有参数；改进非交互式 guardrails，适配脚本化安装
- **Team human coordinators**：Team 资源可含人类协调者成员；Team-admin 拥有的 Matrix 房间 + 更新的 Team Leader / Worker prompts，协调留在 Team Room 内
- **Team Leader coordination refresh**：built-ins 更新（项目规划、DAG 任务执行、文件共享、通信、组织、mcporter 使用、worker 生命周期协调）；反循环回复规则镜像自 Worker
- **CoPaw runtime coordination tools**：task flow、project flow、messaging、file sync、output sanitizing、credential guarding、health probes、readiness handling、可配置 ReAct 迭代上限
- **Nacos remote skills and credentials**：controller 可向 worker 传递 skills API 默认值 + per-package Nacos 认证（`authType=nacos|sts-hiclaw|none`、`ai-registry` STS access scope）
- **Worker identity separation**：controller 资源名与 runtime worker 名解耦（identity、credentials、storage defaults、readiness reporting 全部独立）
- **Controller observability**：per-CRD reconcile metrics、graceful HTTP/background goroutine shutdown、test diagnostics

### 2.4 v1.1.2 Bug 修复（利好本项目）

- `groupAllowFrom` 热加载 —— worker 创建时立即生效
- CoPaw worker 启动期不再吞掉 fresh Matrix 消息
- Controller reconcile 保留 runtime-mutated package 文件和用户插件定制
- TokenReview cache 条目上限 + 清扫（auth 稳定性）
- Higress gateway stream idle timeout 正确应用
- Manager local container 操作改用 controller `/api/v1` 路径
- Rootless Podman socket 检测修复

### 2.5 v1.1.2 需注意的移除项

## 六、收益评估

### 硬收益（可量化）

- 至少 **6 处** patch 可删（can-remove-now 组），**12 处**候选（含 needs-verification），脚本行数预计减少 10–15%
- `MinIO :9000` 与 `local-first merge` 修复让"容器重建后 DM allowlist 回到 `[@admin]`"的运维痛点消失（CLAUDE.md 已记录此 gotcha）
- 上游接管 dispatch 稳定化，可下线 PR #56 中的兜底逻辑
- Controller 可观测性（v1.1.2 新增）替代部分自定义 Prometheus 规则
- `groupAllowFrom` 热加载（v1.1.2）解决 worker 创建后立即需要访问控制的场景

### 软收益

- 控制面与 Phase 1 方向对齐（CRD + Helm）
- 多架构镜像（amd64 + arm64）让本地 Mac 开发体验改善
- `spec.env` 下沉，env-var 管理从脚本侧迁到声明侧
- 为 `analytics-worker` 切 Hermes runtime 留出空间
- Team human coordinators 为未来"人工审核介入"留接口
- Worker identity separation 为未来多 worker 池弹性留空间

### 风险

- `mcpServers` CRD 重构是真正破坏性变化（阶段 1 硬 blocker）；本项目三个 MCP server 的挂载方式必须在分支内验证
- v1.1.0 → v1.1.2 跨 2 个 patch 版本，自动迁移路径在本项目实际拓扑上未亲测（但 v1.1.0 已就位，路径短）
- v1.1.2 Team Leader skill alias 移除 —— 需检查本项目 SOUL.md / SKILL.md 引用
- ECS 单节点 8 GB 内存下多容器拆分，资源占用需在阶段 1 用 `docker stats` 实测后再确认 K8s `resources.requests`
