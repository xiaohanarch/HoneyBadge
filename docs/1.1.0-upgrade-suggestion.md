# HiClaw v1.0.9 → v1.1.0 升级调研与建议

> **结论先行**：推荐升级，但**本周暂不升级**。先闭环当前 `ralph/fix-manager-dispatch` 分支，观察 v1.1.0 社区反馈 1–2 周，下周启动本地验证。

- **调研日期**：2026-04-24
- **当前版本**：HiClaw v1.0.9（2026-04-03 发布）
- **目标版本**：HiClaw v1.1.0（2026-04-24 发布，调研当日）
- **当前分支**：`ralph/fix-manager-dispatch`

---

## 一、v1.1.0 关键变化

**架构性变化（重大）：**
- 从「Manager 单容器 all-in-one」→ **K8s 原生控制面**。Tuwunel / MinIO / Higress / Element Web 从 Manager 中剥离，迁入独立的 `hiclaw-embedded` 容器，Manager 瘦身为纯 Agent 容器（镜像体积 −1.7 GB）
- 新增 CRD 声明式资源（`wk` / `tm` / `hm` / `mgr`），`workers-registry.json` **首次启动时自动迁移到 CRD**
- 插件化 Gateway / Storage Provider；新增 `hiclaw-credential-provider` sidecar
- OpenClaw bundle 升到 `hiclaw-2026.4.14`
- 新 Hermes 自治编码 Worker runtime（与现有 `agent` Node.js runtime 共存）

**对我们直接利好的 Bug 修复：**

| 修复 | 当前项目受影响位置 |
|------|--------------------|
| Controller 不再每 5 分钟轮换 Matrix token（导致 gateway 重启 & 消息丢失） | MEMORY 中记录的「消息顺序冲突 / 热重载」类问题 |
| `allowedConsumers` 在重启时不再被清空 | `init-workers.sh` 当前每次都重建 Higress 路由 |
| `HICLAW_DEFAULT_MODEL` 现在真正被 `hiclaw create worker` 尊重 | `manager-init-internal.sh` Step 2b 手工 patch `openclaw.json` 的 `model.primary` |
| Manager 身份修复为 `@manager`（原 `@default` 丢失 admin DM 消息） | `channels.matrix.dm.allowFrom` 白名单 patch |
| `matrix.autoJoin` 默认 `"always"` | Per-user 账号加不进 DM room 的偶发问题 |
| `HICLAW_OPENAI_BASE_URL` 对非 qwen provider 真正生效 | 当前用 `openai-compat` hack 绕过，可保留但不再必须 |

**破坏性变化（需要适配）：**
- 镜像不再是 all-in-one，`hiclaw-manager:v1.1.0` 不再自带 Tuwunel / MinIO / Higress / Element Web → **docker-compose 与 K8s `manager.yaml` 必须重构**
- `gateway.bind = "lan"` 必须显式设置
- CRD 控制面替代 `workers-registry.json`（自动迁移，但 `init-workers.sh` 的工作方式需重新评估）

## 二、当前项目改动范围评估

| 改动点 | 文件 | 工作量 | 风险 |
|--------|------|--------|------|
| 版本 tag 升级 | `docker-compose.yaml`(3 处)、`k8s/hiclaw/manager.yaml`(1)、`k8s/hiclaw/workers.yaml`(2)、`k8s/jobs/init-workers.yaml`(1)、2 个 Dockerfile、README | 低 | 低 |
| **docker-compose 拆分**：新增 `hiclaw-embedded` 服务，manager 退化为瘦容器 | `deploy/docker/docker-compose.yaml` | **中** | 中（本地 dev 环境重搭） |
| **K8s `manager.yaml` 重构**：Tuwunel / MinIO / Element Web / Higress 抽出为独立 StatefulSet/Deployment（官方推荐用 Helm chart） | `deploy/k8s/hiclaw/*.yaml`、`kustomization.yaml` | **中-高** | 中（ECS 单节点 8 GB 内存，分容器后资源占用需评估） |
| openclaw.json 补丁脚本精简 | `deploy/hiclaw/manager-init-internal.sh` Step 2b / Step 4 | 低 | 低（多个 workaround 可删除） |
| Higress 路由创建脚本精简 | `init-workers.sh` Step 3c | 低 | 低（`allowedConsumers` 不再被抹） |
| CRD 声明式迁移（可选优化） | 新增 `workers.yaml` CRD | 中 | 中（可延后到 Phase 2） |
| 业务层（SOUL.md / dispatch.sh / fast-query.sh / MCP server / adapter） | `hiclaw/manager/agent/**`、`mcp-servers/**`、`src/honeybadge/llm/adapter.py` | 无 | 协议未变，无需改动 |

**兼容性结论**：API / 协议层（Matrix DM、mcporter、MCP SSE、`openclaw.json` schema、Contract 002）**基本兼容**。破坏性集中在**部署拓扑**（单容器 → 多容器）。业务代码零改动。

## 三、收益评估

**硬收益（可量化）：**
- 镜像体积 −1.7 GB，ECS 8 GB 机器的磁盘与 pull 速度有感
- `reasoning` / `token rotation` / `allowedConsumers` 三个我们正在手工修的 bug 原生解决，可删除多个 patch 步骤
- `HICLAW_DEFAULT_MODEL` 生效后，`init-workers.sh` Step 2b / 4 的 JSON patch 逻辑可大幅简化

**软收益：**
- K8s 原生控制面与我们 Phase 1 方向一致（CRD + Helm）
- Hermes runtime 为未来自治 Worker（`analytics-worker` 的 `multi-step-analysis`）打开空间
- 首次启动自动推送 welcome prompt，对新部署体验友好

**风险：**
- v1.1.0 **今日发布**（2026-04-24），零社区反馈，踩坑未知
- 当前 `ralph/fix-manager-dispatch` 分支还有未合入的改动（SOUL.md 路由协议、dispatch scripts、MiniMax-M2.7-highspeed）
- ECS 单节点 8 GB 内存下多容器拆分可能挤占业务资源

## 四、升级建议

**结论：推荐升级，但分两阶段、不要立刻做。**

理由：
1. 现分支存在 uncommitted changes（`SOUL.md` / `dispatch.sh` / `fast-query.sh`），应先闭环当前 manager-dispatch 修复 → PR → merge
2. v1.1.0 刚发布，观察 1–2 周社区反馈（踩 auto-migration 坑的概率较高）
3. 本项目多个 workaround（`reasoning` 移除、`allowedConsumers` 重建、DM 白名单 patch、Manager `baseUrl` 模板）都因 v1.1.0 bug fix 而可删除，**不升级等于持续维护死代码**

## 六、遗留问题：`memorySearch` 的定位

### 当前状态（v1.0.9，`ralph/fix-manager-dispatch`）

`deploy/hiclaw/manager-init-internal.sh` 在启动期把 `agents.defaults.memorySearch` **整段移除**。原因链条：

1. HiClaw v1.0.9 默认模板给 Manager 注入：
   ```json
   "memorySearch": {
     "provider": "openai",
     "model": "text-embedding-v4",
     "remote": { "baseUrl": "http://aigw-local.hiclaw.io:8080/v1", "apiKey": "..." }
   }
   ```
2. 我们的 Higress AI Gateway 只路由 `/v1/chat/completions`，不暴露 `/v1/embeddings`。
3. openclaw 启动时尝试为 memory 文件建索引 → 走 `POST /v1/embeddings` → 路由缺失 → Node `new URL()` 抛 `TypeError: Invalid URL` → **整条 agent run 在第一条用户消息到达时就被打死**（TC105 的根因）。
4. 补丁策略：在 init 脚本的 post-startup patch 块里 `cfg['agents']['defaults'].pop('memorySearch', None)`，让 openclaw 自动进入「无可用 embedding provider → memory search 禁用」分支。

### 为什么选"删除"而不是"改 model"

- `MiniMax-M2.7-highspeed` 是 chat completion 模型，**不是** embedding 模型。即便把 `model` 改成它，openclaw 依然会请求 `/v1/embeddings`，MiniMax gateway 依然不路由，错误只是从 `Invalid URL` 换成 `HTTP 404`，bug 没解决。
- Manager workspace 当前没有 `MEMORY.md` / `memory/*.md`，memorySearch **索引对象为空**。
- Manager SOUL.md 第 32 行（`b729464`, 2026-04-16）显式禁用：
  > *"Never use tools like `exec`, `memory_search`, or `read_file` to try to find ERP data."*
- 这条禁令是 **HoneyBadge 自定义**的，不是 HiClaw 原生。HiClaw 官方模板（`/opt/openclaw/docs/reference/templates/SOUL.md`）反过来是**鼓励**用 memory 文件作为 agent 持久记忆。
- 禁令的原始意图：防止 Manager 用向量命中以前的笔记「幻觉式回答」业务问题，从而绕过 Worker → MCP → NebulaGraph → 审计日志 的强制链路（对应项目防幻觉 5 层框架的 L4 / L5）。

### 1.1.0 升级时需要回头决策的问题

**问题 1：禁令范围是否需要精细化？**

当前禁令原文是 *"to try to find ERP data"*，只限定了 **ERP 业务数据**，没有禁止**运维型记忆**（例："上次这个用户偏好中文表格输出"、"某条 dispatch 规则 90 天内被触发的典型模式"）。

如果未来想保留运维型记忆能力，SOUL.md 应改成：
> *"Never use `memory_search` to retrieve ERP business data (suppliers, orders, invoices, amounts, transactions). It MAY be used to recall operational preferences, routing heuristics, or conversation context signals."*

**问题 2：是否给 Higress 补一条 `/v1/embeddings` 路由？**

需要运维型记忆能力 → 必须有真正的 embedding 后端。候选方案：

| 方案 | baseUrl | API Key | 模型 |
|---|---|---|---|
| DashScope embeddings | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `DASHSCOPE_API_KEY` | `text-embedding-v4` / `text-embedding-v3` |
| MiniMax embeddings | `https://api.minimaxi.com/v1` | `MINIMAX_API_KEY` | `embo-01` 系列（需确认 v1 endpoint 是否兼容 OpenAI schema） |
| 自建 Ollama | `http://ollama.honeybadge.svc/v1` | N/A | `bge-m3` / `mxbai-embed-large`（离线，免密钥） |

**问题 3：memory 文件的写入策略**

`MEMORY.md` 和 `memory/YYYY-MM-DD.md` 一旦启用，需要明确：
- 谁写？Manager agent 自主写，还是运维触发的 offline 流程？
- 写什么？参考 `openclaw/docs/concepts/memory.md` 的 compaction memoryFlush 机制（agent 在会话接近压缩阈值时被系统 prompt 推一次，让它把"要留下的笔记"写到当日文件）
- 审计？memory 文件变更是否进 PostgreSQL 审计日志？（这是绕过 L5 的潜在风险点）

**问题 4：v1.1.0 模板是否已经默认禁用 memorySearch？**

升级本地验证阶段确认一下 `hiclaw-manager:v1.1.0` 启动时生成的 `openclaw.json` 是否还注入 `memorySearch` 默认值。如果 v1.1.0 已经改成"未配置 embedding provider 时不注入 memorySearch"，那 `manager-init-internal.sh` 里的这段 pop 可以直接删。

### 决策矩阵（升级时照此表走）

| 场景 | SOUL 禁令 | runtime memorySearch 配置 | Higress embeddings 路由 | memory 文件 |
|---|---|---|---|---|
| **现状（保持方案）** | 全禁 | 移除 | 不加 | 无 |
| **只解禁运维型记忆** | 限定"ERP 业务数据" | 保留 + 指向真实 embedding | 加 | 加 + 明确写入策略 |
| **完全解禁（不推荐）** | 删禁令 | 保留 | 加 | 加 |

> **1.1.0 升级时的动作项**：在阶段 1 本地验证时评估「问题 4」+ 跑一次真实 embedding 路由（用 DashScope 或 Ollama 方案试跑），然后再决定走哪一列。当前不要把这件事和 TC105 的 blocker 混在一起做。
